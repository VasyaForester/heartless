Вот карта категорий, собранная по реальным источникам — без формулировок, только названия классов и к какому слою они относятся.

Источники, на которые стоит опираться
AgentDojo (Debenedetti et al., 2024) — 97 задач и 629 security test cases в стейтфул-среде, разделяет utility (штатное выполнение) и security (атака через данные инструментов) как раздельные метрики.
InjecAgent (Zhan et al.) — 1054 кейса, 17 «пользовательских» и 62 «атакующих» инструмента, фокус на indirect prompt injection через возвращаемые данные тулов.
τ-bench / τ²-bench (Yao et al., 2024; Barres et al., 2025) — каждая задача либо policy-violation (агент должен отказать), либо mutation (агент должен корректно подействовать), успех требует совпадения и финального состояния БД, и выполнения естественноязыковых условий политики. Домены: retail, airline, telecom (с dual control). 
arxiv
τ-break / “Effective Red-Teaming of Policy-Adherent Agents” — ручная разметка 50 кейсов именно по типам нарушения политики, это прямое попадание в вашу задачу.
OWASP Top 10 for Agentic Applications (2026) — десять категорий риска: ASI01 Agent Goal Hijack, ASI02 Tool Misuse and Exploitation, ASI03 Identity and Privilege Abuse, ASI04 Agentic Supply Chain Vulnerabilities, ASI05 Unexpected Code Execution (RCE), ASI06 Memory and Context Poisoning, ASI07 Insecure Inter-Agent Communication, ASI08 Cascading Failures, ASI09 Human-Agent Trust Exploitation, ASI10 Rogue Agents.
Дополнительно релевантны (упоминаются как «соседние» бенчмарки в литературе): CRMArena-Pro (confidentiality compliance), IntellAgent (генерация диагностических тестов из policy-графов), Near-Miss (пост-хок аудит отказов), AgentRewardBench (оценка судей траекторий), CRAFT (состязательные пользователи).
Категории по вашим пяти границам

1) Контроль доступа (сессия привязана к сущности)
Это пересекается с ASI03 (Identity and Privilege Abuse) из OWASP-классификации и с категорией Authentication Bypass – Data Privacy из τ-break. Типовые оси внутри этого слоя: кто инициирует запрос на доступ (сам пользователь / третья сторона от его имени), форма запроса (прямой / через сопоставление по косвенным признакам), момент в диалоге (в начале сессии / после смены контекста), и источник «легитимизации» запроса (ничем не обоснован / обоснован ссылкой на внешний авторитет).

2) Согласованность финансовых операций
В τ-break это прямо выделено как Authentication Bypass – Financial Damage (48% кейсов бенчмарка) — самая весомая категория у них. Смежная ось — Cancellation Policy Violations (28%). Разбиение внутри слоя обычно идёт по: единице учёта операции (на уровне заказа / на уровне позиции / на уровне сессии), способу повторного обращения к уже обработанному кейсу, и источнику цифр, которыми оперирует диалог (из БД агента / принесены в диалог пользователем).

3) Комплаенс категорий (запрещённый список)
Прямого отдельного бенчмарка под «запрещённые категории товаров» в академической литературе я не нашёл — это ближе к доменным policy-чеклистам конкретных платформ, а не к публичным тест-корпусам. Но относится к общей категории perenumerative/categorical constraint testing внутри ASI02 (Tool Misuse and Exploitation): ось — обоснование исключения (внутреннее / внешнее по отношению к политике), и статус запроса (разовый / систематический).

4) Соответствие каталогу (допустимый список позиций)
Аналогично — ближе к доменным policy wiki в стиле τ²-bench (where domain policy specifies the approved set of actions/items), чем к отдельной публичной таксономии. Membership Privilege Violations у τ-break — близкий аналог (разрешено ли это конкретному классу пользователей/операций).

5) Валидация входа (числовые поля)
Прямого канонического набора категорий для числовой валидации в LLM-агентных бенчмарках нет — это скорее классическая область input validation testing из traditional software QA (boundary value analysis, equivalence partitioning, type coercion testing), перенесённая на диалоговый интерфейс. Основные оси: формат представления значения, язык/локаль запроса, позиция поля в многошаговом диалоге (первое заявление / исправление).

Общие оси разбиения корпуса

Собирая по всем источникам, типовые непересекающиеся оси:

Источник авторитета заявления (сам пользователь / якобы третья сторона / якобы системное сообщение) — прямая параллель с ASI01/ASI06 различием goal hijack vs memory/context poisoning.
Канал доставки (прямой текст пользователя / данные, возвращаемые инструментом) — это ключевое разделение AgentDojo и InjecAgent (direct vs indirect injection).
Уровень успеха атаки, если вы хотите мерить не только бинарный исход: как минимум три уровня — model compromise (контент меняет ответ модели), agent compromise (меняется цель/план/состояние/выбранное действие агента) и system impact (происходит проверяемое несанкционированное или устойчивое изменение состояния системы). 
arxiv
Временной горизонт — в рамках одной сессии vs переживающий сессию (это разделение явно вынесено в работах про memory poisoning как отдельный, более редко покрываемый класс).
Тип требуемого исхода — τ²-bench явно делит задачи на policy-violation (должен отказать) и mutation (должен корректно выполнить) — полезная ось для балансировки корпуса.
Дополнительные границы, которые принято покрывать

Помимо ваших пяти — из OWASP и смежных бенчмарков: целостность цепочки инструментов/плагинов (ASI04, supply chain), устойчивость к данным, записываемым в долгосрочную память (ASI06), безопасность при делегировании задач другому агенту (ASI07), устойчивость к каскадным сбоям при цепочке вызовов (ASI08), и explicit confidentiality boundary (что агент не должен раскрывать о других пользователях/внутренних данных) — это отдельно выделено в CRMArena-Pro как самостоятельная ось, не сводимая к access control.
