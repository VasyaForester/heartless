Я бы строил этот корпус не как коллекцию способов сформулировать подозрительный запрос, а как таксономию нарушаемых бизнес-инвариантов.

Это важное различие: десять вариантов просьбы «сделайте исключение» не обязательно дают десять классов покрытия. Зато повтор операции после тайм-аута и параллельное выполнение двух операций могут выглядеть почти одинаково на уровне диалога, но проверять разные механизмы защиты.

Ниже я разделяю:

- класс диалога — самостоятельная ситуация, в которой проверяется определённая граница;
- слой защиты — механизм, который должен обеспечить корректный исход;
- вариацию — другой язык, канал, источник утверждения или формулировка того же класса.

Учитываю перечисленные вами существующие тесты и стараюсь не повторять их.

# 1. Доступ только к своей области

Основной слой: привязка сессии к пользователю, объектная авторизация, изоляция контекста и ролей.

Помимо уже имеющихся проверок, я бы добавил следующие семейства.

| Класс                                          | Что проверяет                                                                                         |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Межсессионная утечка контекста                 | Не переносит ли бот данные одного пользователя в другую сессию                                        |
| Смена пользователя без пересоздания сессии     | Сохраняется ли привязка к первоначальной идентичности                                                 |
| Истечение сессии                               | Не продолжает ли бот использовать прежнюю авторизацию после её истечения                              |
| Повторная аутентификация                       | Не считает ли бот старый контекст достаточным после изменения состояния авторизации                   |
| Межканальный перенос идентичности              | Не переносит ли бот полномочия между чатом, веб-интерфейсом и другим каналом                          |
| Ролевая эскалация                              | Не принимает ли бот утверждение о повышении роли за фактическое изменение полномочий                  |
| Конфликт ролей                                 | Разделяет ли бот полномочия пользователя и другого участника сессии, представителя или сотрудника     |
| Неявное делегирование                          | Отличает ли бот упоминание доверенного лица от реально зарегистрированного делегирования полномочий   |
| Связанный чужой объект                         | Проверяет ли принадлежность не только основного объекта, но и связанных с ним сущностей               |
| Межпользовательские связи                      | Не считает ли наличие общей операции, контрагента или переписки основанием для доступа к чужим данным |
| Утечка через агрегаты                          | Не раскрывает ли бот сведения о чужих объектах через сводки, количество записей и результаты поиска   |
| Утечка через побочные результаты               | Сохраняется ли ограничение при формировании документов, экспорте и уведомлениях                       |
| Смешение идентичностей при продолжении диалога | Не приписывает ли бот текущему пользователю действия, совершённые в другом контексте                  |

Особенно важные дополнительные разрезы:

1. Сессия активна / истекла / восстановлена.
2. Один пользователь / связанный пользователь / делегат / сотрудник.
3. Прямой объект / связанный объект / коллекция объектов.
4. Чтение / проверка существования / вычисление / изменение / экспорт.

Отдельно отмечу: проверка принадлежности связанного объекта и проверка принадлежности основного объекта — разные классы. Бот может правильно идентифицировать владельца заказа, но ошибочно использовать другой связанный аккаунт при последующей операции.

# 2. Одна выплата на операцию

Основные слои: арифметическая сверка, согласованность учётных записей, управление состоянием операции, идемпотентность.

Здесь особенно важно разделить арифметические ошибки и ошибки управления транзакциями. Калькулятор может правильно посчитать сумму, но бот всё равно может повторно выполнить уже завершённую операцию.

| Класс                                   | Что проверяет                                                                                                   |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Повтор завершённой операции (replay)    | Не создаётся ли вторая выплата при повторении уже исполненного запроса                                          |
| Повтор после неопределённого результата | Сверяет ли бот фактическое состояние операции, если первоначальный ответ был неполным или потерян               |
| Конкурирующие выплаты                   | Сохраняется ли единственность при одновременном поступлении нескольких запросов                                 |
| Накопление частичных выплат             | Учитывает ли бот все ранее выполненные частичные выплаты при расчёте доступного остатка                         |
| Суммирование по позициям                | Не превышает ли совокупная выплата допустимую величину при распределении суммы между позициями заказа           |
| Распределение скидки                    | Корректно ли рассчитывается возмещаемая сумма при наличии скидок на заказ или отдельные позиции                 |
| Распределение налогов и доставки        | Не возникает ли превышение из-за повторного включения налогов, доставки и иных составляющих                     |
| Валютная точность                       | Корректно ли обрабатываются разряды валюты, округление и накопительные погрешности                              |
| Состояние исходного платежа             | Отличает ли бот оплаченный, неоплаченный, отменённый, оспоренный и уже возмещённый заказ                        |
| Состояние выплаты                       | Различает ли бот созданную, ожидающую, исполненную, отклонённую и отменённую операцию                           |
| Несогласованность реестров              | Как бот поступает, когда сумма или состояние в учётном реестре расходятся с текстовым утверждением пользователя |
| Откат частичного исполнения             | Не оставляет ли бот несогласованные записи, когда одна часть многошаговой операции завершилась, а другая нет    |
| Межканальное дублирование               | Не создаёт ли второй возврат при обращении по той же операции через другой канал                                |
| Изменение исходных данных               | Пересчитывает ли бот допустимый остаток при изменении подтверждённой суммы заказа или истории выплат            |
| Смешение валют и единиц учёта           | Не складывает ли бот суммы разных валют либо значения в разных представлениях без корректного приведения        |

### Приоритетные пробелы

Я бы в первую очередь добавил пять классов:

1. Повтор после неопределённого результата. Это не то же самое, что повтор уже подтверждённой операции.
2. Конкурирующие выплаты. Отдельная проверка атомарности.
3. Накопление частичных выплат. Отличается от проверки лимита одной выплаты.
4. Распределение скидок, налогов и доставки. Проверяет правильность происхождения итоговой суммы.
5. Согласованность реестров. Проверяет, кому бот доверяет при конфликте текстового утверждения и учётных данных.

Для этой границы полезна концепция business invariants: проверяются не только числа, но и допустимые переходы между состояниями. OWASP отдельно выделяет повтор завершённых операций, гонки, атомарность и идемпотентность как типовые проблемы бизнес-логики.&#x20;

# 3. Запрещённая категория размещения

Основные слои: перечислительные запреты, классификация сущностей, проверка фактической категории, независимость решения от заявленной цели.

У вас уже хорошо представлены попытки обосновать исключение внутренней или тестовой целью. Я бы расширил покрытие в другую сторону: как бот определяет саму принадлежность товара к запрещённой категории и насколько последовательно применяет запрет.

| Класс                              | Что проверяет                                                                                                           |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Семантический эквивалент категории | Распознаёт ли бот категорию при отличающемся наименовании или терминологии                                              |
| Алиасная классификация             | Учитывает ли зарегистрированные синонимы, торговые и технические обозначения                                            |
| Иерархия категорий                 | Распространяется ли запрет на дочерние категории, если это предусмотрено политикой                                      |
| Неоднозначная категория            | Умеет ли бот распознать ситуацию, когда описание соответствует нескольким категориям                                    |
| Составной товар                    | Как применяется запрет к комплекту, в котором присутствует запрещённая составляющая                                     |
| Отдельная комплектующая            | Различает ли бот самостоятельную допустимую комплектующую и запрещённый товар                                           |
| Вариативность исполнения           | Учитывает ли категорию конкретная модификация или функциональный вариант товара                                         |
| Конфликт названия и атрибутов      | Что происходит, когда заголовок указывает на одну категорию, а характеристики — на другую                               |
| Конфликт текста и изображения      | Насколько последовательно бот классифицирует товар при расхождении визуальных и текстовых сведений                      |
| Ошибка категории продавца          | Проверяет ли бот фактическую принадлежность вместо безусловного доверия выбранной продавцом категории                   |
| Запрещённое в ином формате         | Сохраняется ли классификация при изменении формата предложения: продажа, аренда, обмен, дарение или объявление о поиске |
| Географическое расхождение         | Не подменяет ли бот внутреннюю политику утверждением о допустимости товара в другой юрисдикции                          |
| Изменение категории объявления     | Повторно ли проверяется классификация после изменения характеристик или содержания публикации                           |
| Повторная публикация               | Сохраняется ли запрет при повторном размещении того же товара в другом объявлении                                       |
| Пограничная разрешённая категория  | Отличает ли бот запрещённый объект от близкого, но разрешённого объекта                                                 |
| Изменение версии классификатора    | Не использует ли бот устаревшую классификацию или уже отменённое правило                                                |

Особенно рекомендую добавить три самостоятельные группы:

- Состав и комплектность: запрещённый элемент в комплекте, частичная комплектация, комплектующие.
- Расхождение признаков: название, категория, описание, атрибуты и визуальное представление.
- Пограничная классификация: запрещённая сущность против похожей разрешённой сущности.

Последняя группа важна не меньше отрицательных тестов. Иначе можно получить бота, который хорошо отказывает, но чрезмерно блокирует законные объявления.

Применимость отдельных классов зависит от конкретного текста политики: например, нельзя автоматически считать комплектующую запрещённой только потому, что запрещён самостоятельный товар.

# 4. Предмет вне каталога

Основные слои: сверка с утверждённой матрицей, сохранение идентичности предмета, контроль допустимых атрибутов и полноты исходных данных.

В отличие от предыдущей границы, здесь предмет необязательно запрещён вообще. Он может быть просто не предусмотрен конкретной программой или матрицей.

| Класс                              | Что проверяет                                                                                                                                 |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Неполное совпадение с каталогом    | Не приравнивает ли бот похожий объект к разрешённому без достаточных оснований                                                                |
| Неоднозначное соответствие SKU     | Корректно ли обрабатывает ситуацию, когда одному наименованию соответствуют несколько позиций                                                 |
| Вариант вне матрицы                | Различает ли бот разрешённую модель и неподдерживаемую модификацию той же модели                                                              |
| Изменение поколения или редакции   | Не переносит ли допустимость старой версии автоматически на новую                                                                             |
| Алиас товара                       | Различает ли фактический предмет и его альтернативное коммерческое наименование                                                               |
| Комплект из разных категорий       | Не распространяется ли допустимость одной позиции на весь комплект                                                                            |
| Комплектующая отдельно             | Не переносит ли бот правила для целого изделия на самостоятельную комплектующую                                                               |
| Неполная комплектация              | Учитывает ли отсутствие обязательных составляющих предмета                                                                                    |
| Количественная вариативность       | Сохраняется ли допустимость для заданного количества единиц или частей одного предмета                                                        |
| Вариативность состояния            | Различает ли бот состояния нового, бывшего в употреблении, повреждённого или неполного предмета, если матрица устанавливает такие ограничения |
| Отсутствующие характеристики       | Выбирает ли бот уточнение вместо необоснованного признания предмета допустимым                                                                |
| Противоречивые характеристики      | Не принимает ли наиболее выгодный для совершения операции атрибут при наличии противоречащих данных                                           |
| Устаревшая позиция                 | Проверяет ли бот актуальность каталога при работе с выведенными из обращения позициями                                                        |
| Будущая позиция                    | Не считает ли бот анонсированный или планируемый объект уже включённым в действующую матрицу                                                  |
| Региональная вариативность матрицы | Учитывает ли бот применимую версию каталога для конкретного региона или программы                                                             |
| Изменение матрицы во времени       | Не применяет ли бот старые условия к операции, для которой должна действовать новая версия правил                                             |
| Подмена предмета в ходе диалога    | Сохраняет ли бот идентичность первоначально указанного предмета на последующих этапах                                                         |
| Множественные предметы             | Проверяет ли бот допустимость каждой позиции отдельно, а не распространяет результат проверки одного предмета на остальные                    |

### Что здесь особенно важно

Я бы выделил три независимых измерения:

1\. Идентичность предмета.

Товар, его модификация, комплект и комплектующая не должны автоматически считаться одной сущностью.

2\. Полнота информации.

Есть три различных состояния:

- предмет однозначно соответствует матрице;
- предмет однозначно не соответствует матрице;
- имеющихся данных недостаточно для решения.

Третье состояние не следует автоматически засчитывать как успешное отклонение или разрешение. Корректным исходом может быть запрос недостающих характеристик.

3\. Актуальность допустимости.

Один и тот же предмет может иметь разный статус в зависимости от версии матрицы, программы и даты применения правил.

Это позволяет тестировать именно сверку с бизнес-данными, а не только способность цитировать каталог.

# 5. Строгая валидация числовых полей

Основные слои: типизация, синтаксический разбор, нормализация, проверка диапазонов, семантическая валидация.

У вас уже есть проверка положительности, знаков и некоторых Unicode-представлений. Поэтому я не повторяю варианты записи минуса и сосредотачиваюсь на остальных пробелах.

| ---------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Смешение числового и строкового типа     | Отличает ли бот число от строки, содержащей числовое представление                                     |

| Отсутствующее значение                   | Отличает ли бот отсутствие параметра от явно заданного значения                                        |
| Null-значение                            | Корректно ли обрабатывает отсутствие числового значения в структурированном вводе                      |
| Экспоненциальная запись                  | Допустима ли научная форма записи для конкретного поля                                                 |

| Разделители групп разрядов               | Не интерпретирует ли бот разделитель тысяч как десятичный знак                                         |
| Смешение форматов записи                 | Корректно ли обрабатываются значения с неоднозначным сочетанием десятичных и группирующих разделителей |

| Округление и усечение                    | Не изменяет ли бот значение при автоматическом преобразовании точности                                 |
| Переполнение                             | Корректно ли отклоняются значения за пределами представимого числового типа                            |
| Непредставимые конечные значения         | Обрабатывает ли бот NaN, Infinity и аналогичные нечисловые специальные значения                        |
| Граничные значения диапазона             | Различает ли значения непосредственно ниже границы, на границе и выше неё                              |
| Культурно-зависимый формат числа         | Учитывает ли заданную локаль при интерпретации десятичного разделителя и группировки разрядов          |

| Числовой диапазон                        | Отличает ли бот одно значение от интервала значений                                                    |
| Арифметическое выражение вместо значения | Отличает ли валидатор числовое значение от текстового выражения                                        |
| Несовместимые единицы измерения          | Не принимает ли числовое значение с неподходящей единицей или размерностью                             |
| Согласованность нескольких полей         | Проверяет ли бот взаимозависимости числовых параметров, а не только каждый параметр отдельно           |
| Множественные значения в структуре       | Проверяет ли бот каждый элемент массива, вложенного объекта или набора параметров                      |
| Неизвестные дополнительные поля          | Не использует ли бот неподдерживаемые числовые атрибуты как источник значения                          |
| Повторяющиеся параметры                  | Корректно ли обрабатывает повторное появление одного поля с различными значениями                      |
| Избыточная длина представления           | Не принимает ли бот слишком длинное или неподдерживаемое представление числа                           |

### Дополнительные оси для числовых тестов

Здесь я бы обязательно разделял несколько понятий:

| Ось         | Значения                                                  |
| ----------- | --------------------------------------------------------- |
| Тип         | Integer, decimal, float, string, boolean, null            |
| Знак        | Положительное, ноль, отрицательное                        |
| Диапазон    | Ниже минимума, минимум, внутри, максимум, выше максимума  |
| Точность    | Допустимая, избыточная, потеря точности                   |
| Формат      | Обычный, экспоненциальный, группированный, локализованный |
| Локаль      | Точка, запятая, различные группировочные разделители      |
| Размер      | Нормальный, очень большой, переполнение                   |
| Размерность | Ожидаемая, другая, отсутствующая                          |
| Структура   | Одиночное поле, несколько полей, вложенная структура      |

Важное замечание: знак и диапазон нельзя объединять в один класс. Значение `0` может иметь корректный числовой тип, но быть недопустимым по бизнес-правилу. Аналогично отрицательное значение может быть технически корректным числом, но недопустимым для конкретного поля.

# 6. Общая методика разбиения корпуса

Теперь самое важное: как организовать все эти семейства так, чтобы они не пересекались и покрытие можно было измерить.

Я предлагаю использовать двухуровневую схему.

## Уровень A. Основная таксономия: что именно проверяем

Каждый тест получает ровно один основной класс по нарушаемому инварианту.

Например:

| Граница     | Основной класс                        | Проверяемый инвариант                                              |
| ----------- | ------------------------------------- | ------------------------------------------------------------------ |
| Доступ      | Межсессионная утечка                  | Пользователь не получает контекст другой сессии                    |
| Выплаты     | Replay операции                       | Завершённая операция не исполняется повторно                       |
| Маркетплейс | Составной товар                       | Запрещённая составляющая не получает исключение через комплект     |
| Каталог     | Неоднозначное соответствие SKU        | Неизвестный предмет не приравнивается автоматически к разрешённому |
| Валидация   | Дробное значение в целочисленном поле | Недопустимый тип значения не принимается                           |

Это помогает избавиться от искусственного увеличения покрытия за счёт перефразирования.

## Уровень B. Ортогональные оси вариаций

Каждый основной класс дополнительно размечается тегами.

Я бы использовал следующие оси:

| Ось                      | Возможные значения                                                                 | Для чего нужна                                   |
| ------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------ |
| Канал доставки           | Прямой диалог, цитата, документ, вложение, внешний источник, результат инструмента | Проверка устойчивости к происхождению информации |
| Источник авторитета      | Пользователь, бот, внутренняя БД, регламент, сотрудник, внешний источник           | Проверка иерархии доверия                        |
| Тип утверждения          | Факт, просьба, разрешение, исключение, подтверждение, предположение                | Проверка реакции на содержание сообщения         |
| Объект воздействия       | Аккаунт, операция, заказ, товар, поле, связанная сущность                          | Проверка предметной области                      |
| Состояние процесса       | Не начат, начат, ожидает, завершён, отменён, просрочен                             | Проверка временного и транзакционного состояния  |
| Авторизация              | Текущий пользователь, другой пользователь, делегат, другая роль, истёкшая сессия   | Проверка границ полномочий                       |
| Степень определённости   | Однозначно допустимо, однозначно недопустимо, недостаточно данных, конфликт данных | Проверка правильности решения                    |
| Временная характеристика | До операции, во время, после, повтор, параллельное исполнение                      | Проверка последовательности событий              |
| Диалоговая структура     | Один ход, несколько ходов, изменение условий, противоречие, уточнение              | Проверка устойчивости на протяжении диалога      |
| Языковая вариативность   | Один язык, переключение языка, синонимы, профессиональная терминология             | Проверка семантического понимания                |
| Формат представления     | Текст, структурированные данные, таблица, изображение, смешанный формат            | Проверка зависимости от представления            |

Важный принцип: одна и та же вариация не должна автоматически становиться самостоятельным классом.

Например, «межсессионная утечка через текст» и «межсессионная утечка через вложение» могут быть двумя реализациями одного класса с разными тегами `канал доставки`. Но если система имеет независимые механизмы обработки вложений и текста, их стоит дополнительно выделить в отдельные подклаccы для технического покрытия.

## Как считать покрытие

Я бы разделил три метрики:

1\. Таксономическое покрытие

\\[ C\_{\text{class}} = \frac{\text{число покрытых классов}} {\text{число определённых классов}} \\]

Это отвечает на вопрос, насколько полно описано пространство проверок.

2\. Покрытие вариаций

\\[ C\_{\text{variation}} = \frac{\text{проверенные сочетания тегов}} {\text{запланированные сочетания тегов}} \\]

Например, класс уже присутствует, но проверялся только в одном канале и только при активной сессии.

3\. Повторяемость корректного исхода

Для каждого теста полезно проводить несколько независимых прогонов и фиксировать долю правильных результатов. Особенно для вероятностных моделей.

Не стоит смешивать эти показатели в один процент: наличие класса в корпусе ещё не означает, что бот стабильно проходит соответствующую проверку.

# 8. Какую структуру я бы выбрал для вашего корпуса

Мой итоговый вариант организации:

| Поле                   | Назначение                                       |
| ---------------------- | ------------------------------------------------ |
| `boundary_id`          | Одна из пяти границ                              |
| `class_id`             | Уникальный класс проверки                        |
| `parent_class_id`      | Родительское семейство                           |
| `primary_layer`        | Основной слой защиты                             |
| `secondary_layers`     | Дополнительные проверяемые механизмы             |
| `scenario_state`       | Исходное состояние бизнес-процесса               |
| `input_channel`        | Канал поступления информации                     |
| `authority_source`     | Источник утверждения                             |
| `dialogue_pattern`     | Одноходовый или многоходовый сценарий            |
| `expected_outcome`     | Допустимое действие, отказ, уточнение, эскалация |
| `expected_state`       | Ожидаемое конечное состояние системы             |
| `side_effects_allowed` | Допустимые изменения состояния                   |
| `risk_weight`          | Важность нарушения проверяемого инварианта       |

Я бы также закрепил четыре правила тест-дизайна.

Первое. Один основной инвариант на тест.

Сценарий может проверять несколько защитных механизмов, но для подсчёта покрытия ему назначается один основной класс. Остальные отмечаются как дополнительные. Иначе один сложный тест искусственно закроет сразу несколько независимых пробелов.

Второе. Положительные контрольные случаи.

Для каждой запрещённой ситуации должен существовать близкий допустимый сценарий. Особенно важно для маркетплейса, каталога и числовой валидации: проверяется не только способность отказать, но и способность не отказывать там, где ограничение неприменимо.

Третье. Отдельно фиксировать четыре исхода.

- `ALLOW` — штатное выполнение.
- `REFUSE` — корректное отклонение.
- `CLARIFY` — запрос недостающих данных.
- `ESCALATE` — передача человеку или другой процедуре.

Нельзя считать любой отказ правильным результатом. Например, при неизвестном товаре в каталоге уточнение может быть правильнее безусловного отказа.

Четвёртое. Проверять конечное состояние, а не только сообщение.

Для выплаты недостаточно ответа «операция выполнена один раз»: нужно проверить число фактически созданных операций и учётный остаток. Для доступа недостаточно отказа: нужно проверить отсутствие утечки. Для каталога нужно проверить, что исходная идентичность предмета не изменилась.

Это особенно хорошо согласуется с подходом τ-bench и ToolSandbox.

## Мой приоритет пополнения корпуса

## Первый эшелон

Классы с высокой ценностью для проверки независимых механизмов защиты

1. Межсессионная утечка контекста.
2. Ролевая эскалация.
3. Повтор после неопределённого результата выплаты.
4. Конкурирующие выплаты.
5. Накопление частичных выплат.
6. Расхождение текстовой и фактической классификации товара.
7. Составной товар с запрещённой составляющей.
8. Неоднозначное соответствие предмета каталогу.
9. Изменение версии матрицы во времени.
10. Неявное преобразование числового типа.
11. Дробное значение в целочисленном поле.
12. Локализованные числовые разделители.
    ## Второй эшелон
    Географические и межканальные различия, устаревшие позиции, визуальная классификация, специальные числовые представления, повторяющиеся параметры, округление и размерность.

Главный вывод: у вас уже достаточно хорошо представлены вариации формулировок, попытки обоснования исключений и непосредственные проверки значений. Наибольший прирост полноты дадут новые типы бизнес-состояний, отношения между объектами, конфликты источников данных и случаи недостаточной определённости.

Иными словами, я бы расширял корпус прежде всего по семантическим и транзакционным классам, а не по числу новых формулировок одного и того же запроса.
