# Рекомендации по развитию учебного harness

Я бы не стал дальше наращивать farm и heal отдельными функциями. Сейчас у вас уже появился небольшой исполнительный комплекс, которому не хватает трёх вещей: единой модели состояния, надёжного контура сверки результатов и планировщика, который управляет всем жизненным циклом попытки.

Оптимальная цель: превратить набор скриптов в локальную систему управления экспериментами. Она должна знать, что запланировано, что реально отправлено, к какому диалогу относится ответ, какая оценка ожидается, что уже получено и какие действия допустимы после сбоя.

Важное архитектурное решение: разделить три сущности:

- Attempt — попытка выполнить сценарий на конкретной модели.
- Dialog — диалог на полигоне, в котором может быть несколько сообщений.
- Evaluation — результат автоматической оценки диалога или попытки. У него могут быть отдельные идентификатор, время появления и несколько версий при переоценке.

Это сразу решит часть проблем с доп-ходами, повторными оценками и задержками результатов.

## 1. Целевая архитектура

Предлагаю следующую схему:

CLI / Queue Manager

Запуск, поиск диалогов, очередь, повторные операции, отчёты

Runner

Выполнение попыток, контроль переходов, чекпойнты

Reconciler

Сверка оценок, поиск пропусков, обработка ожиданий

Dialog Manager

Поиск, чтение, доп-ходы, переоценка

Analytics

Конкретность, профили моделей, диагностика каналов

Storage: SQLite + журнал событий

Единое состояние, история операций, результаты, метрики

Один браузерный драйвер, общий для всех компонентов, с единым адаптером интерфейса полигона.

### Главный принцип

Не давать farm, heal, CLI и парсеру самостоятельно менять одни и те же записи. Они должны обращаться к общим сервисам и репозиториям.

Например, farm не должен самостоятельно решать, что попытка завершена. Он передаёт runner информацию о полученном ответе. Runner меняет состояние попытки, а reconciler независимо находит и связывает результат оценки.

Это позволит отдельно тестировать навигацию, отправку, чтение ответов и обработку оценок.

## 3. Схема данных и единое состояние

### 3.1. Основные таблицы

Я бы использовал SQLite с такими сущностями:

| Таблица           | Назначение                    | Ключевые поля                                                                  |
| ----------------- | ----------------------------- | ------------------------------------------------------------------------------ |
| `scenarios`       | Реестр сценариев              | `scenario_id`, `name`, `version`, `difficulty`, `priority`, `max_attempts`     |
| `models`          | Список моделей                | `model_id`, `provider`, `name`, `enabled`, `profile_id`                        |
| `runs`            | Запуски farm                  | `run_id`, `started_at`, `finished_at`, `config_hash`, `status`                 |
| `dialogs`         | Диалоги на полигоне           | `dialog_id`, `external_id`, `model_id`, `scenario_id`, `created_at`            |
| `attempts`        | Попытки выполнения сценариев  | `attempt_id`, `run_id`, `dialog_id`, `state`, `prompt_hash`, `started_at`      |
| `messages`        | Сообщения внутри диалогов     | `message_id`, `dialog_id`, `sequence`, `role`, `content`, `created_at`         |
| `evaluations`     | Автоматические оценки         | `evaluation_id`, `external_id`, `dialog_id`, `status`, `score`, `observed_at`  |
| `pending_results` | Ожидающие оценки              | `pending_id`, `attempt_id`, `next_poll_at`, `poll_count`, `deadline`, `status` |
| `events`          | Неизменяемая история действий | `event_id`, `entity_id`, `event_type`, `timestamp`, `payload`                  |

Отдельно:

- `model_profiles` — поведенческие профили моделей.
- `channel_observations` — результаты проверки каналов передачи текста.
- `feature_snapshots` — признаки ответа на момент расчёта скоринга.
- `predictions` — прогноз вероятности успеха с указанием версии модели.
- `queue_jobs` — задания планировщика и их состояние.

### 3.2. Журнал попыток

Текущую запись JSONL стоит расширить. Пример логической записи:

```
{
  "attempt_id": "att_20261107_001",
  "run_id": "run_20261107_01",
  "scenario_id": "scenario_014",
  "scenario_version": "2",
  "model_id": "provider_model_x",
  "dialog_id": "dlg_7812",
  "template_id": "template_03",
  "template_version": "4",
  "channel": "user_message",
  "state": "awaiting_evaluation",
  "prompt_hash": "sha256:...",
  "response_hash": "sha256:...",
  "started_at": "2026-11-07T15:00:00Z",
  "sent_at": "2026-11-07T15:00:08Z",
  "response_at": "2026-11-07T15:00:21Z",
  "evaluation_status": "pending",
  "retry_count": 0,
  "labels": {
    "evaluation_success": null,
    "manual_review": false
  }
}
```

Важные дополнения:

1\. Версионирование сценария и шаблона. Если изменить текст задания, результат уже нельзя безоговорочно сравнивать с предыдущими запусками.

2\. Хеширование исходного текста и ответа. Это позволит обнаруживать повторную отправку и одинаковые результаты без постоянного сравнения больших строк.

3\. Разделение состояния попытки и состояния оценки. Полученный ответ не означает, что оценка готова.

4\. Хранение доп-ходов отдельно. Уточняющее сообщение — это новая запись в `messages`, а не новая попытка. В противном случае вы потеряете связь между первоначальным ответом и окончательной оценкой диалога.

### 3.3. Реестр ожидающих результатов

`pending_results` должен быть полноценным рабочим реестром, а не просто списком ID, ожидающих ответа.

Пример:

```
{
  "pending_id": "pend_001",
  "attempt_id": "att_20261107_001",
  "dialog_id": "dlg_7812",
  "expected_type": "evaluation",
  "first_seen_at": "2026-11-07T15:00:21Z",
  "last_polled_at": "2026-11-07T15:01:00Z",
  "next_poll_at": "2026-11-07T15:02:00Z",
  "poll_count": 3,
  "deadline": "2026-11-08T15:00:21Z",
  "status": "waiting"
}
```

Предлагаемые статусы:

| Статус      | Значение                                 |
| ----------- | ---------------------------------------- |
| `waiting`   | Оценка ещё не найдена                    |
| `found`     | Найдена и сопоставлена                   |
| `ambiguous` | Найдено несколько возможных соответствий |
| `expired`   | Время ожидания истекло                   |
| `cancelled` | Ожидание отменено                        |
| `error`     | Ошибка чтения списка оценок              |

Важная деталь: истечение срока ожидания не должно автоматически превращать результат в отрицательный. Это отдельный статус, а не `fail`.

### 3.4. Реестр событий

Помимо итоговых записей, очень рекомендую сделать append-only таблицу `events`.

Примеры типов событий:

```
run.created
navigation.started
navigation.verified
attempt.send_intent
attempt.sent
attempt.response_received
attempt.awaiting_evaluation
evaluation.discovered
evaluation.matched
evaluation.orphaned
evaluation.reassessed
attempt.recovered
attempt.failed
```

События помогут восстановить последовательность действий после сбоя и понять, на каком этапе возникла проблема. Текущее состояние попытки при этом хранится в `attempts`, а история переходов — в `events`.

## 4. Reconciler: автоматическая сверка оценок

Это одна из первых функций, которую я бы реализовал. Именно она уберёт наиболее неприятную ручную работу.

### Логика работы

```
Получить список оценок из интерфейса
              |
              v
     Нормализовать записи
              |
              v
  Найти соответствие в журнале
              |
       +------+------+
       |             |
    Найдено       Не найдено
       |             |
       v             v
   Проверить      Создать запись
   соответствие   orphan evaluation
       |
   +---+---+
   |       |
  Да     Несколько
   |       |
   v       v
 Обновить  ambiguous
 журнал   -> ручная проверка
```

### Алгоритм сопоставления

Использовать последовательные уровни достоверности:

1. Точное соответствие: внешний ID диалога или оценки.
2. Сильное соответствие: ID модели + ID сценария + временной диапазон + идентификатор диалога.
3. Резервное соответствие: модель + время + хеш или характерный фрагмент ответа.

Последний вариант нельзя автоматически принимать при неоднозначности.

Для каждой связи хранить:

```
{
  "match_method": "external_dialog_id",
  "match_confidence": 1.0,
  "matched_at": "2026-11-07T15:03:00Z"
}
```

В интерфейсе стоит показывать отдельно:

- оценки, которые есть в журнале;
- оценки, которых нет в журнале;
- попытки, для которых оценка ожидается;
- оценки, которые нельзя однозначно связать;
- записи, которые выглядят дублирующимися.

Не создавайте фиктивную попытку при обнаружении оценки без записи в журнале. Создавайте `orphan evaluation` с доступными данными и пометкой `needs_review`. Иначе в статистике появятся попытки, которые фактически не запускались или не имеют известного исходного текста.

### Интерфейс модуля

```
class EvaluationReconciler:    def scan(self) -> list[EvaluationRecord]:        ...    def normalize(self, raw_records) -> list[EvaluationRecord]:        ...    def match(self, record) -> MatchResult:        ...    def reconcile(self, records=None) -> ReconcileSummary:        ...    def list_orphans(self) -> list[EvaluationRecord]:        ...    def list_unresolved(self) -> list[PendingResult]:        ...
```

### Периодическая обработка

Сделать отдельный worker, который получает только записи со статусом `waiting`.

Пример графика опроса:

| Возраст ожидания  | Следующий опрос |
| ----------------- | --------------- |
| До 1 минуты       | Через 15 секунд |
| 1–5 минут         | Через 1 минуту  |
| 5–30 минут        | Через 5 минут   |
| 30 минут – 2 часа | Через 15 минут  |
| Более 2 часов     | Через 1 час     |

После обнаружения оценки worker закрывает ожидание, обновляет журнал и пишет событие `evaluation.matched`. После установленного срока ожидания запись получает `expired`, но не исчезает из реестра.

Параметры опроса должны находиться в YAML, а не быть зашиты в код.

## 5. Навигация и Dialog Manager

### 5.1. Разделить навигацию и выполнение

Сейчас ошибка «контекст сценария изменился» говорит о том, что farm недостаточно доверяет состоянию страницы.

Предлагаю перед каждым раундом вызывать обязательный `ensure_context()`.

Он должен проверять:

- открыт ли правильный раздел полигона;
- загружен ли нужный сценарий;
- совпадает ли его идентификатор;
- выбранная модель соответствует конфигурации;
- доступно ли поле ввода;
- нет ли незавершённого действия на предыдущей странице;
- не осталось ли старого диалога, в который случайно уйдёт новое сообщение.

Проверка должна основываться в первую очередь на стабильных идентификаторах элементов страницы и URL/маршруте, а не только на видимом заголовке.

Пример интерфейса:

```
class NavigationManager:    def ensure_section(self, section_id): ...    def open_scenario(self, scenario_id): ...    def verify_context(self, scenario_id, model_id): ...    def get_page_state(self): ...    def recover_context(self, expected_context): ...
```

`farm` должен получать от него структурированный результат:

```
{
  "valid": true,
  "section_id": "training",
  "scenario_id": "scenario_014",
  "model_id": "provider_model_x",
  "composer_available": true,
  "active_dialog_id": null,
  "checks_passed": 6,
  "checks_failed": 0
}
```

Если `valid=false`, отправка запрещается. Это не ситуация для оптимистичной попытки или повторного нажатия кнопки.

### 5.2. Единый Dialog Manager

Я бы выделил работу с диалогами в самостоятельный сервис, не привязанный к farm.

Его интерфейсы:

```
harness dialog find \
  --model provider_model_x \
  --scenario scenario_014 \
  --since 2026-11-07

harness dialog show \
  --dialog dlg_7812 \
  --format full

harness dialog read \
  --dialog dlg_7812 \
  --last 5

harness dialog followup \
  --dialog dlg_7812 \
  --template clarification_01 \
  --reason incomplete_response

harness dialog evaluate \
  --dialog dlg_7812

harness dialog history \
  --dialog dlg_7812 \
  --format json
```

`followup` должен автоматически создавать сообщение в существующем `dialog_id`, сохранять его хеш и фиксировать причину доп-хода. При этом надо отдельно учитывать версию диалога, на которой была получена оценка.

Переоценка тоже должна создавать новую запись в `evaluations`, а не перетирать предыдущую. Так вы сможете оценивать стабильность самого оценщика.

## 6. Скоринг конкретности и предиктор успешной оценки

Здесь я бы сделал два самостоятельных инструмента. Не стоит смешивать качество ответа с вероятностью того, что ответ получит положительную оценку.

### 6.1. Скоринг конкретности

Назначение: измерить, насколько ответ содержит проверяемую операционную информацию, а не общие рассуждения.

Предлагаю шкалу от 0 до 100.

| Признак                     | Вес | Что измерять                                     |
| --------------------------- | --- | ------------------------------------------------ |
| Числа и единицы измерения   | 18% | Числовые значения с осмысленными единицами       |
| Последовательность действий | 18% | Шаги, порядок, этапы                             |
| Параметры                   | 15% | Названия параметров и конкретные значения        |
| Ожидаемые результаты        | 14% | Что должно получиться после действия             |
| Проверка результата         | 12% | Критерии проверки, контрольные условия           |
| Примеры                     | 10% | Конкретные примеры, демонстрации                 |
| Ограничения и условия       | 8%  | Предпосылки, границы применимости                |
| Структурированность         | 5%  | Таблицы, списки, блоки последовательных действий |

Это начальные веса, а не установленные закономерности. Их необходимо проверить на ваших размеченных ответах.

Например, два ответа могут быть одинаковой длины, но один содержит общие советы, а второй — последовательность из пяти действий с параметрами, ожидаемыми результатами и критериями проверки. Второй должен получить существенно более высокий балл.

Какие признаки извлекать:

```
features = {    "answer_length": 0,    "numeric_values": 0,    "numeric_with_units": 0,    "ordered_steps": 0,    "named_parameters": 0,    "parameter_values": 0,    "expected_outputs": 0,    "verification_conditions": 0,    "examples": 0,    "constraints": 0,    "structured_blocks": 0}
```

Рекомендую использовать гибрид:

- Regex для числовых значений, единиц измерения, конструкций `параметр = значение`.
- Простой парсер Markdown для списков, заголовков и таблиц.
- Небольшой классификатор или фиксированный словарь для распознавания действий, условий и проверок.
- LLM-оценщик как дополнительный экспериментальный компонент, а не источник единственной истины.

Счёт каждого признака нужно нормировать и ограничивать сверху, иначе длинные ответы будут автоматически получать преимущество.

Например:

\\[ S=100\cdot\sum\_{i=1}^{8}w_i\cdot f_i \\]

где \\(w_i\\) — вес признака, \\(f_i\\) — его нормированное значение от 0 до 1.

Важный нюанс: число само по себе не является операционной конкретикой. Число без контекста, единицы измерения или привязки к действию не должно давать много баллов.

### 6.2. Предиктор вероятности успешной оценки

При 90 размеченных попытках я бы пока не использовал CatBoost, Random Forest, XGBoost или нейросети. Выборка слишком мала, чтобы уверенно обучать сложные зависимости.

Начальный вариант — логистическая регрессия с L2-регуляризацией.

Целевая переменная:

```
evaluation_success:
    1 = положительная оценка
    0 = отрицательная оценка
    null = нет достоверной оценки
```

В обучающий набор не должны попадать ожидающие, потерянные и неоднозначные результаты.

Предлагаемые признаки:

| Признак                   | Источник            |
| ------------------------- | ------------------- |
| `specificity_score`       | Собственный скоринг |
| `answer_length_log`       | Ответ               |
| `ordered_steps`           | Ответ               |
| `numeric_with_units`      | Ответ               |
| `verification_conditions` | Ответ               |
| `model_stability_rate`    | Реестр профилей     |
| `scenario_difficulty`     | Реестр сценариев    |
| `channel_compatibility`   | Карта каналов       |

На первых 90 наблюдениях не использовал бы все восемь признаков одновременно. Начал бы с 4–6 наиболее устойчивых, чтобы не переобучиться.

Пример:

```
from sklearn.pipeline import make_pipelinefrom sklearn.preprocessing import StandardScalerfrom sklearn.impute import SimpleImputerfrom sklearn.linear_model import LogisticRegressionmodel = make_pipeline(    SimpleImputer(strategy="median"),    StandardScaler(),    LogisticRegression(        C=0.5,        penalty="l2",        max_iter=1000    ))model.fit(X_train, y_train)probabilities = model.predict_proba(X_test)[:, 1]
```

Это базовая реализация. Для категориальных признаков потребуется предварительное кодирование. Не стоит бездумно превращать каждую модель и каждый сценарий в отдельный признак: на 90 записях такая матрица будет разреженной.

### 6.3. Как правильно проверить модель на 90 записях

Главная проблема — утечка информации между обучением и тестированием.

Например, если ответы одного сценария окажутся одновременно в обучающей и тестовой выборках, модель может выучить особенности этого сценария, а не общие закономерности успешной оценки.

Предлагаю:

1. Сначала сравнить качество логистической регрессии с простым базовым правилом: прогноз только по конкретности.
2. Использовать 5-fold Stratified Group Cross Validation с группировкой по сценарию или семейству сценариев, когда число групп позволяет это сделать.
3. Дополнительно провести отдельную проверку обобщения на моделях, не встречавшихся в обучающей части, если наблюдений для этого достаточно.
4. Рассчитать PR-AUC, ROC-AUC, Brier Score и матрицу ошибок.
5. Проверить калибровку вероятностей и разброс метрик между фолдами.

Для вероятностного прогноза особенно важен Brier Score: он показывает, насколько предсказанные вероятности соответствуют фактическим исходам.

Как использовать прогноз:

| Вероятность       | Решение                                           |
| ----------------- | ------------------------------------------------- |
| Высокая           | Оставить обычный процесс, приоритет на выполнение |
| Средняя           | Отправить на дополнительную проверку              |
| Низкая            | Проверить полноту ответа и корректность контекста |
| Модель не уверена | Не принимать автоматическое решение               |

Конкретные пороги надо подобрать на валидации, а не назначать заранее.

### 6.4. Дополнительный ход как отдельный эксперимент

Развернуть ответ подробнее иногда полезно, но я бы не внедрял доп-ход безусловно.

Ввести отдельную политику:

```
followup_policy:
  enabled: true
  max_followups_per_dialog: 1
  only_if:
    - low_specificity
    - incomplete_answer
  require:
    - scenario_allows_followup
    - dialog_context_verified
  record_outcome_separately: true
```

Главное — измерять, изменил ли доп-ход результат оценки.

Накапливать статистику:

```
original_specificity
followup_specificity
original_evaluation
final_evaluation
followup_used
evaluation_delta
```

Тогда вы сможете сравнить результаты с доп-ходом и без него, не смешивая исходные ответы и ответы после дополнительного взаимодействия.

## 7. Карта каналов обработки Unicode и разметки

Это отдельный диагностический модуль, не часть farm.

Я бы разделил три понятия:

- `fixture` — конкретный тестовый текст;
- `surface` — место передачи текста: пользовательское сообщение, поле внутри ответа и т. п.;
- `observation` — фактический результат обработки.

Для диагностики используйте контролируемые тестовые строки с заранее известными ожидаемыми Unicode-последовательностями. Цель — проверить сохранение, нормализацию и отображение тестового текста, а не подбирать способы обхода защитных механизмов.

### Структура таблиц

`channel_observations`:

| Поле                   | Значение                         |
| ---------------------- | -------------------------------- |
| `observation_id`       | ID проверки                      |
| `model_id`             | Модель                           |
| `provider_version`     | Версия провайдера, если известна |
| `surface`              | Поверхность передачи             |
| `fixture_id`           | ID тестовой строки               |
| `sent_hash`            | Хеш исходного текста             |
| `received_hash`        | Хеш наблюдаемого текста          |
| `expected_length`      | Ожидаемая длина                  |
| `observed_length`      | Фактическая длина                |
| `replacement_count`    | Количество U+FFFD                |
| `normalization_status` | Результат проверки нормализации  |
| `result`               | Итог проверки                    |
| `tested_at`            | Время тестирования               |

Ключевой момент: сохранять не только визуально отображаемый текст, но и последовательность кодовых точек там, где интерфейс и используемый инструмент это позволяют.

### Результирующая матрица

Иллюстрация формата, не реальные результаты ваших моделей.

| Модель  | User message | Поле ответа  | Статус        |
| ------- | ------------ | ------------ | ------------- |
| Model A | Exact        | Normalized   | Проверять     |
| Model B | Partial loss | Exact        | Проверять     |
| Model C | Exact        | Exact        | Совпадение    |
| Model D | Replacement  | Partial loss | Потеря данных |

Я бы предусмотрел четыре класса результата:

- `exact` — последовательность сохранена;
- `normalized` — преобразована ожидаемым образом;
- `partial_loss` — часть содержимого потеряна;
- `invalid` — результат не соответствует ожидаемой обработке.

И отдельный класс `inconclusive`, если невозможно получить достоверное наблюдение.

Важно: результат зависит не только от модели, но и от конкретной версии поверхности передачи, промежуточного интерфейса и даты проверки. Поэтому карту нужно регулярно обновлять, а не считать вечным свойством модели.

## 8. Поведенческие профили моделей

Создать реестр `model_profiles`, который обновляется на основании фактической статистики, а не вручную по впечатлениям.

Пример:

```
{
  "model_id": "provider_model_x",
  "profile_version": 3,
  "observations": 18,
  "behavior": {
    "cautious_template_rate": 0.35,
    "neutral_response_rate": 0.55,
    "empty_response_rate": 0.10,
    "timeout_rate": 0.05
  },
  "reliability": {
    "successful_requests": 17,
    "failed_requests": 1,
    "median_latency": 12.4
  },
  "status": "active",
  "updated_at": "2026-11-07T15:00:00Z"
}
```

Здесь есть тонкость: доли разных поведенческих классов и технические ошибки лучше хранить раздельно. Один ответ может быть осторожным и одновременно технически корректным.

Я бы выделил следующие характеристики:

| Характеристика      | Что измерять                                   |
| ------------------- | ---------------------------------------------- |
| Стабильность        | Доля пустых ответов и ошибок                   |
| Осторожность        | Частота шаблонных ограничений                  |
| Полнота             | Доля ответов с достаточным содержанием         |
| Структурированность | Частота последовательных и проверяемых ответов |
| Скорость            | Медиана и p95 времени ответа                   |
| Каналы              | Наблюдаемое поведение по каждой поверхности    |

### Stop-list и circuit breaker

Не делал бы постоянный чёрный список на основании одной неудачи.

Лучше три состояния:

- `active` — обычная работа;
- `cooldown` — временно исключена из очереди;
- `disabled` — исключена до ручного включения.

Например, если за последние 10 запросов накопилось 4–5 пустых ответов, а наблюдений достаточно для такого вывода, модель отправляется на временную паузу. При следующем периоде можно провести контрольную проверку.

Порог должен быть конфигурируемым, а решение — сопровождаться причиной:

```
provider_model_x -> cooldown
reason: elevated_empty_response_rate
observations: 10
empty_responses: 5
```

Это лучше, чем просто сообщение «модель нестабильна».

## 9. Queue Manager: планирование и приоритизация

Это следующий крупный модуль после reconciler.

Очередь должна учитывать не только сложность сценария, но и стоимость попытки, состояние модели и лимит повторов.

### 9.1. Модель задания

```
{
  "job_id": "job_001",
  "scenario_id": "scenario_014",
  "model_id": "provider_model_x",
  "priority": 50,
  "difficulty": 2,
  "estimated_cost": 1,
  "max_attempts": 3,
  "attempts_completed": 0,
  "status": "queued",
  "created_at": "2026-11-07T15:00:00Z"
}
```

### 9.2. Очередность

Предлагаю разделить сценарии на четыре класса:

| Класс      | Характеристика                  | Когда запускать        |
| ---------- | ------------------------------- | ---------------------- |
| Quick wins | Простые, дешёвые, стабильные    | Первыми                |
| Standard   | Обычная сложность               | После quick wins       |
| Advanced   | Дорогие или сложные             | После основной очереди |
| Tail       | Повторные и нестабильные случаи | В отдельном цикле      |

Не стоит навсегда закреплять за сценарием один класс. Его можно менять по накопленной статистике успешности и затрат.

### 9.3. Приоритет

В качестве первого варианта:

\\[ P=\frac{W_p\cdot W_i\cdot W_h}{C} \\]

Где:

- \\(W_p\\) — приоритет сценария;
- \\(W_i\\) — ценность получения результата или информации;
- \\(W_h\\) — коэффициент технической готовности модели;
- \\(C\\) — ожидаемая стоимость выполнения.

Чтобы очередь не зацикливалась на дешёвых сценариях, добавить aging — увеличение приоритета задания по мере его ожидания.

Но важно: техническую нестабильность модели не нужно приравнивать к низкой вероятности положительной оценки. Это два разных фактора.

### 9.4. Пример конфигурации

```
scheduler:
  max_parallel_drivers: 1
  order: priority_then_cost
  aging_enabled: true

  defaults:
    max_attempts: 3
    max_retries: 2

  execution:
    simple_first: true
    defer_advanced: true
    tail_queue_enabled: true

  retry_policy:
    navigation_error: retry
    read_timeout: retry
    evaluation_timeout: pending
    uncertain_send: reconcile_before_retry
    provider_empty_response: cooldown_check

  limits:
    max_attempts_per_scenario_model: 3
    max_followups_per_dialog: 1
```

### 9.5. Интерфейс команд

```
# Создать очередь из выбранных сценариев и моделей
harness queue build \
  --scenarios active \
  --models enabled

# Просмотреть очередь
harness queue list

# Посмотреть план без выполнения
harness queue plan --dry-run

# Запустить очередь
harness queue run

# Посмотреть хвосты
harness queue list --status deferred,failed

# Повторить подходящие задания
harness queue retry --eligible-only

# Отложить сложные задания
harness queue defer --class advanced
```

Обязательно сохранять `selection_reason`: почему конкретное задание было выбрано следующим. Это сильно поможет при анализе поведения планировщика.

## 11. Надёжность: самые важные инженерные изменения

Здесь есть несколько вещей, которые важнее самого ML.

### 11.1. Защита от двойной отправки

Это, вероятно, главный риск текущего farm.

Нельзя полагаться на то, что после сбоя достаточно проверить последний чекпойнт и продолжить с того же места.

Рекомендую использовать устойчивый идентификатор операции:

```
idempotency_key =
hash(
  run_id +
  scenario_id +
  model_id +
  template_version +
  replicate_number
)
```

При повторном запуске задания его ключ должен сохраняться. Новый ключ создаётся только для намеренно новой попытки.

Критически важная логика:

Перед нажатием кнопки отправки система записывает в БД состояние `send_intent`. После подтверждения отправки — `sent`.

Если процесс упал между этими событиями, состояние становится `uncertain_send`.

В этом случае:

1. Не отправлять текст повторно.
2. Проверить текущий диалог.
3. Найти сообщение по времени, хешу и последовательности.
4. Если отправка обнаружена — восстановить статус `sent`.
5. Если результат однозначно установить нельзя — отправить на ручную проверку.

Абсолютная гарантия exactly-once в браузерном интерфейсе недостижима без поддержки идемпотентности самим полигоном. Поэтому лучше обеспечить at-most-once при неопределённом результате, чем случайно продублировать сообщение.

### 11.2. Восстановление после сбоя

Нужен отдельный метод:

```
class RecoveryManager:    def inspect_interrupted_jobs(self): ...    def recover_sent_attempts(self): ...    def recover_pending_evaluations(self): ...    def reconcile_browser_state(self): ...    def produce_recovery_report(self): ...
```

При запуске harness:

```
1. Проверить блокировку драйвера.
2. Найти незавершённые операции.
3. Проверить фактическое состояние браузера.
4. Восстановить подтверждённые отправки.
5. Пометить неоднозначные как uncertain.
6. Пересчитать pending_results.
7. Продолжить допустимые задания.
```

Не нужно автоматически перезапускать все задания со статусом `failed`: сначала следует классифицировать причину ошибки.

### 11.3. Управление одним драйвером

Поскольку браузер пока один, очередь должна быть строго последовательной.

Нужно добавить:

- глобальную блокировку браузерного драйвера;
- heartbeat текущего процесса;
- идентификатор владельца блокировки;
- тайм-аут блокировки;
- запрет второго farm-процесса;
- запрет одновременной работы heal и CLI над одной вкладкой.

Heal лучше превратить в часть общего orchestration loop. Он может наблюдать состояние, но не должен самостоятельно конкурировать с farm за управление страницей.

### 11.4. Логирование

Вместо разрозненных текстовых логов — JSON-структуры.

Каждая запись должна иметь:

```
{
  "timestamp": "2026-11-07T15:00:00Z",
  "level": "INFO",
  "run_id": "run_01",
  "attempt_id": "att_001",
  "component": "navigation",
  "event": "context_verified",
  "duration_ms": 840,
  "status": "success"

```

Ввести единый справочник ошибок:


Не сохранять секреты авторизации и чувствительные данные браузерной сессии в диагностических снимках. Для скриншотов и сырого содержимого предусмотреть локальные права доступа и сроки хранения.

### 11.5. Тестирование

Добавить фикстуры HTML/JSON для:

- разных состояний страницы;
- изменённого расположения элементов;
- нескольких вариантов списка оценок;
- задержанной оценки;
- пустого ответа;
- незавершённой отправки;
- повторяющихся оценок;
- смены контекста сценария.

Особенно рекомендую тестировать восстановление после искусственного падения процесса на каждом переходе:

```

after navigation
before send
after send intent
after actual send
after response
before evaluation
after evaluation discovery
```

Это позволит проверить, не возникают ли дубли и потерянные попытки.

## 12. Приоритет внедрения

Я бы не пытался реализовать всё одновременно. Оптимальный порядок следующий.

## Этапы модернизации

1. Этап 1. Единая модель данных

   Самый высокий приоритет

   SQLite, единые ID, разделение Attempt / Dialog / Evaluation, миграция существующего JSONL, журнал событий.

   Результат: единое состояние экспериментов.
2. Этап 2. Надёжность и навигация

   `NavigationManager`, проверка контекста, защита от двойной отправки, RecoveryManager, блокировка одного драйвера.

   Результат: воспроизводимый запуск без случайных дублей.
3. Этап 3. Reconciler и Pending Manager

   Автопарсинг оценок, точное сопоставление, orphan-записи, периодические проверки, статусы неоднозначности.

   Результат: исчезает ручная сверка журнала и оценок.
4. Этап 4. Dialog Manager и CLI

   Поиск, чтение, история диалогов, доп-ходы, повторные оценки.

   Результат: единая точка управления всеми операциями.
5. Этап 5. Queue Manager и отчёты

   Приоритеты, бюджеты попыток, обработка хвостов, circuit breaker, автоматические сводки.

   Результат: управляемое выполнение экспериментов.
6. Этап 6. Аналитика

   Скоринг конкретности, карта каналов, профили моделей, baseline-предиктор.

   Результат: статистически обоснованное планирование и сравнение результатов.

## 14. Мой главный совет: что делать прямо сейчас

Я бы начал с четырёх вещей, именно в таком порядке:

Первое — SQLite и единая модель Attempt / Dialog / Evaluation. Это фундамент. Без него остальные модули будут продолжать создавать несовместимые записи.

Второе — Reconciler + Pending Manager. Это даст наиболее заметный эффект на повседневной работе: автоматическое обнаружение задержанных оценок, сопоставление с журналом и отсутствие ручной сверки.

Третье — Navigation Guard + защита от двойной отправки. Это устранит часть потерь попыток и повысит воспроизводимость.

Четвёртое — единый Dialog Manager CLI. После этого farm перестанет быть единственным способом управлять экспериментами.

Аналитический блок я бы не торопился усложнять. На 90 размеченных попытках уже можно реализовать скоринг конкретности и получить первый baseline логистической регрессии. Но до накопления дополнительных независимых наблюдений предиктор стоит считать исследовательской подсказкой, а не механизмом принятия решений.

Итоговая архитектурная идея: сделать harness системой с единым состоянием эксперимента, независимыми исполнительными модулями и отдельным аналитическим контуром. Тогда добавление новых сценариев, моделей и диагностических инструментов не потребует очередного набора разовых скриптов.
